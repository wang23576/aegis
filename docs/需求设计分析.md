## 3. 角色与权限模型

### 3.1 三角色（单角色制）

| 角色 | 用户管理 | 智能体管理 | 智能体内部资源 | 会话 |
| --- | --- | --- | --- | --- |
| 超级管理员 | 创建用户、授予角色（含超管） | 创建 + 管理**全部**智能体 | 全部 | 仅自己（Q5 默认） |
| 智能体管理员 | 无 | 创建 + 仅管理**自己创建**的智能体 | 仅自己智能体下 | 自己智能体下的 |
| 普通用户 | 无 | 无 | 无 | 仅自己的会话历史 |

### 3.2 权限 = 功能权限 + 数据归属

```
授权判定 = 角色具备该操作能力  AND  数据归属满足（agent.owner_id == 当前用户 id）

超管：角色通过 + 归属检查豁免
智能体管理员：角色通过 + 归属检查必须通过
普通用户：角色不通过（无管理入口），仅会话数据归属自己
```

**归属设计**：`agent.owner_id` 为归属源；workspace / skill / subagent / session 通过 `agent_id` 归属于智能体，权限沿 `agent → owner_id` 传递，不冗余存 owner。

### 3.3 数据模型草图（单角色版）

```
user (id, username, password_hash, role, created_at)   —— role 单值：SUPER_ADMIN / AGENT_ADMIN / USER
agent (id, name, owner_id, config, created_at)
workspace (id, agent_id, path, ...)
skill (id, agent_id, ...)
subagent (id, agent_id, ...)
session (id, agent_id, user_id, workspace_id, ...)
```

## 7. LLM 操作权限三档（agentscope-java 原生）

### 7.1 档位映射（已定三档）

| 前端档位 | 框架 `PermissionMode` | 只读工具 | 写工具（写文件/shell） | deny 规则与危险路径 |
| --- | --- | --- | --- | --- |
| 仅可查看 | `EXPLORE` | 放行 | **拒绝**（引擎硬编码） | 仍生效 |
| 工作区修改 | `ACCEPT_EDITS` | 放行 | **默认 ASK**（无 allow 规则时） | 仍生效 |
| 完全权限 | `BYPASS` | 放行 | **放行** | 仍生效，**不可绕过** |

**关键源码实证（2026-11-24 核对）：**
- `PermissionEngine.java:232-252`：`EXPLORE` 对非只读工具直接返回 DENY——这是引擎硬实现，最可靠。
- `PermissionEngine.java:253-264`：`ACCEPT_EDITS` 在工具自检阶段**只放行只读工具**，对写工具返回 `null` 继续往后走。
- `PermissionEngine.java:201-205`：没有 allow 规则命中时，最终落 `defaultDecisionAsk()` → **ASK**。
- `PermissionEngine.java:191-199`：`BYPASS` 在 allow 规则之后兜底无条件 ALLOW，但 `checkDenyRules`（`:268-279`）在流水线最前面，故 deny 不可绕过。
- `ReActAgent.java:6285-6346`：`setPermissionMode(userId, sessionId, mode)` 按会话切换并持久化。

**重要澄清（纠正枚举注释的误导）**：`PermissionMode` 注释写 `ACCEPT_EDITS = file edits inside working directories are auto-allowed`，但引擎实现并未自动放行工作区内写操作。要兑现该语义，必须靠：工具的 `checkPermissions()` 结合工作目录、预置 allow 规则、或路径策略/沙箱。**三档中只有 EXPLORE 与 BYPASS 是引擎级确定性行为，ACCEPT_EDITS 是"半档"，需要平台补齐。**

### 7.2 平台层需补齐

1. 三档 → mode 映射与下发（调用 `setPermissionMode`，按会话持久化）。
2. `ACCEPT_EDITS` 的"工作区内写操作免确认"需平台补齐：预置 allow 规则 + `PathPolicy` + 工具自检（见 R1）。
3. 审批 UI：框架提供 `PERMISSION_ASKING` + `ConfirmResult` 协议，**不含 UI**，需平台实现。
4. 档位存储与会话绑定。

## 7A. 多用户共享智能体的文件落点与隔离（源码实证）

> 2026-11-24 新增。回答「多个用户针对同一 agent，本机 + shell 模式下资料放哪里、如何隔离」。

### 7A.1 数据落点

| 数据类型 | 落点 | 是否按用户隔离 |
| --- | --- | --- |
| 会话日志 journal | `<workspace>/<userId>/.agentscope-runtime/agents/<agent>/sessions/<user>/<session>/threads/<thread>/`（Windows 为 `journal.sqlite3`） | 是（双重编码） |
| AgentState | `~/.agentscope/state/<agentId>/<userId>/<sessionId>/agent_state.json` | 是 |
| 对话产物 artifacts | `<workspace>/<userId>/outputs/...`（workspace 内普通文件，无固定目录） | 是 |
| memory / 每日日志 | `<workspace>/<userId>/MEMORY.md`、`memory/YYYY-MM-DD.md` | 是 |
| tasks | `<workspace>/<userId>/agents/<agentId>/tasks/<sessionId>.json` | 是 |
| **公共静态资产** | `<workspace>/AGENTS.md`、`skills/`、`subagents/`、`knowledge/`、`tools.json` | **否，全局共享** |

关键源码：`ThreadKey.java:33-42`（路径含 user/session）、`WorkspaceManager.java:248-266`（namespace 前缀）、`HarnessAgent.java:1472-1505`（workspace 解析）。

### 7A.2 隔离机制与边界

- `isolationScope` 四档：`USER`（默认，namespace=userId）/ `SESSION`（namespace=sessionId）/ `AGENT` / `GLOBAL`（后两者**无路径前缀，各用户混在一起**）。本机默认值 = USER。
- 文件工具在 `ROOTED`（默认）模式下：`applyNamespacePrefix` 给相对路径加用户前缀，`requireOwnNamespace` 阻止用绝对路径访问他人目录（issue #3261）。
- 可选项 `projectWritable(true)`：把产物写 `<project>/<ns>/`，元数据留 `<workspace>/<ns>/`，实现"用户产物 vs agent workspace"物理分离。

### 7A.3 与产品要求的冲突（重点）

**产品要求**：用户对话只能影响自己会话的文件；智能体 workspace 下的资源（skills/subagents 等）不应被用户对话影响。

**冲突**：本机 + shell 模式下，shell 工具 `execute` 是宿主 `cmd.exe /c` / `sh -c`（`LocalFilesystemWithShell.java:320-347`），**不做任何 namespace / PathPolicy 检查**，cwd 默认在 `project`（`${user.dir}`，无用户前缀），可 `cd ..` 或用绝对路径改写 `<workspace>/skills/`、`AGENTS.md`。文件工具的路径防护对 shell 完全无效。

> 这与上一轮 Q13「不强制沙箱」的决策直接矛盾：选了不沙箱，就无法靠框架满足文件隔离要求。类注释亦明确警告 "no sandboxing, process isolation, or security restrictions"（`LocalFilesystemWithShell.java:46-49`）。

**Q14 已定（2026-11-24）**：保留 shell 能力、不上 Docker 沙箱，采用 `isolationScope=USER` 用户隔离；越界改写共享区作为**已知优化点后续处理**，测试阶段专门做攻击测试验证边界。以下为当时评估过的备选方案，留档备查：
1. 禁用 shell 工具 + `isolationScope(SESSION)` + `projectWritable(true)` —— 未采纳（不禁用 shell）。
2. Docker 沙箱 + `IsolationScope.SESSION` + 静态资产 readOnly 挂载 —— 未采纳（不上 Docker）。
3. 维持现状接受风险 —— **已采纳**，但转为"主动攻击测试 + 后续优化"的正面策略。

### 7A.4 隔离粒度精确表（USER scope，源码核实）

| 数据类型 | 隔离粒度 | 同一用户跨 session | 不同用户之间 | 源码依据 |
| --- | --- | --- | --- | --- |
| 会话日志 journal | **user + session 双层** | 隔离（各自 thread） | 隔离 | `ThreadKey.java:33-42` |
| AgentState / 权限档位 | **user + session 双层** | 隔离 | 隔离 | `JsonFileAgentStateStore.java:55-66`；`ReActAgent.java:6304` |
| 对话产物 outputs | user（namespace） | **共享同一目录** | 隔离 | `WorkspaceManager.java:248-266` |
| MEMORY.md / memory/ | user（namespace） | **共享**（设计意图：跨会话记忆） | 隔离 | `WorkspaceManager.java:420` |
| AGENTS.md / skills/ / subagents/ / knowledge/ | 全局 | 共享 | **共享（可被 shell 越界改写）** | §7A.1 |

**结论**：会话状态和日志按 `(userId, sessionId)` 严格隔离，绝不串；只有"记忆类"和"输出产物"是按 userId 隔离、同一用户跨会话共享。这正是 USER scope 的语义。

**前端注意**：权限档位也存在 session 级（`setPermissionMode(userId, sessionId, mode)`）——用户在 A 会话选"完全权限"，B 会话不会继承。切换会话时须按会话读取当前档位再回显，不能沿用上一个会话的值。

### 7A.5 攻击测试（学习 agentscope-java 的刻意实践）

在测试阶段专门验证以下越界场景，把"拦不住"的边界变成可复现的测试用例，为后续优化提供依据：

- [ ] 用户 A 会话用 shell `cd ..` 或绝对路径改写 `<workspace>/skills/`，验证用户 B 下次调用是否读到被改版本
- [ ] shell 改写 `AGENTS.md` / `tools.json` 的效果与传播范围
- [ ] 文件工具（非 shell）用绝对路径访问 `<workspace>/<其他userId>/`，验证 `requireOwnNamespace` 是否拦住
- [ ] 用户 A、B 同一智能体同时开会话，各自 outputs/ 与 MEMORY.md 是否互不干扰
- [ ] 切换 session 后权限档位是否正确回显（不应继承）

> 定位：这些是**学习性验证**，不是上线阻断项；结果为后续优化（如 shell 路径策略、只读挂载）提供输入。

## 7B. 内置工具与默认智能体（2026-11-24 新增，已确认方向）

### 7B.1 内置工具：直接用框架原生

**结论：agentscope-java 原生提供 45+ 个内置工具，paw 用的就是这些，Aegis 直接复用，不需自研。** 注册主入口 `HarnessAgent.java:3283-3362`。

paw 默认 agent 的 `tools.json`（`scaffold/default/tools.json`）白名单 16 个：

| 类别 | 工具名 | readOnly | 功能 |
| --- | --- | --- | --- |
| 文件 | `read_file` / `write_file` / `edit_file` / `list_files` / `grep_files` / `glob_files` | 前 1+3 只读，写2个否 | 读写/搜索文件 |
| 执行 | `execute` | 否 | shell 命令（本项目保留，见 Q14） |
| 网络 | `web_fetch` / `web_search` | 是 | 抓网页 / 联网搜索（search 需 API Key） |
| 记忆 | `memory_search` / `memory_get` / `memory_save` | 前2只读 | 长期记忆读写 |
| 会话 | `thread_search` / `thread_list` / `thread_history` | 是 | 历史会话检索 |

框架还有但未列入 paw 默认白名单的：plan 三件套（`plan_enter/write/exit`）、任务类（`task_output/cancel/list`、`wait_async_results`）、子 agent 类（`agent_spawn/send/release/list`）、`team`、`skill_manage`/`propose_skill`、`load_skill_through_path`、`deliver_artifact`、`todo_write`（默认 OFF）。可按智能体需要加入白名单。

### 7B.2 不同智能体选不同工具（框架原生支持）

- **主途径**：每个 agent 独立 workspace 的 `tools.json`，用 `allow`/`deny` 白黑名单控制（`ToolsConfig.java:36-58`、`ToolFilter.java:55-80`）。`deny` 永远优先；`allow` 非空时只放行列出的工具（平台编排工具默认豁免）。
- 子 agent 可在声明里写 `tools: [read_file, grep_files]` 做白名单（`AgentSpecLoader.java:329`）。
- 编程式：`builder.toolsConfig(...)` / `disableXxxTools()`。
- Aegis 落地：智能体管理页提供工具勾选，保存到该 agent 的 `tools.json`（复用 paw 的 `GET/PUT /api/agents/{id}/tools/config` 思路）。

### 7B.3 内置工具"小标志"（平台层需实现）

**框架没有内置标志元数据**：`@Tool` 注解和 `ToolSchema` 都没有 `isBuiltin/source/category` 字段。paw 的做法是平台层硬编码一份内置名单 + 前端 badge（不完整，只覆盖 12 个）。

**Aegis 方案**：平台维护一份完整的 `BUILTIN_TOOLS` 注册表（按 §7B.1 全集 + `HarnessPlatformTools.NAMES`），前端展示工具清单时对命中名单的显示"内置"小标志，MCP/自定义工具显示不同标志。框架侧可提供 `Toolkit.getToolSchemas()` 拿当前 agent 实际可用工具列表。

### 7B.4 默认智能体 claw（归属超级管理员 admin）

paw 的 claw 是启动自动生成的单用户内置 agent（id=`default`，name=`claw`，无 owner，前端标 built-in）。**Aegis 的差异：要纳入用户体系，归属超管 `admin`。**

设计：
- 系统初始化时，由启动引导逻辑创建默认智能体 `claw`（**id = `claw`**），`owner_id = admin 用户 id`，标记 `builtin=true`（UI 显示"内置"标志）。
- workspace 从 `scaffold/default` 拷贝：`AGENTS.md`（通用助手人格）、`tools.json`（§7B.1 的 16 个工具白名单）、`skills/example-skill`、`subagents/README.md`、`memory/`。
- claw 对所有普通用户可见可用（作为默认选择），但只有超管能改其配置；智能体管理员按 owner 规则管不到它（owner=admin）。
- 其它模板智能体（blank / customer-support / research-assistant）本期不做，仅留 claw 一个默认。

**Q15 已定**：claw 的 id = `claw`（Alan 拍板，2026-11-24）。
